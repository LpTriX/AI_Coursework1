\section{Part 1A: Sudoku as a CSP}
Sudoku has 81 variables $X_{r,c}$, one per cell, where r and c range from 1 to 9. An empty cell has domain $\{1,\ldots,9\}$; a given digit fixes its cell to a singleton domain. Zero denotes an empty input cell and is never a solution value [1-3].

There are 27 AllDifferent constraints: one for each of nine rows, nine columns and nine 3-by-3 boxes. Together with the domains, these require each unit to contain every digit exactly once. A completion must preserve all original givens.

Let m be the number of empty cells. Enumerating every digit assignment gives $9^m$ complete candidates. Under fixed-size board checking, this yields a coarse $O(9^m)$ upper bound. The unpruned backtracking tree has at most $1+9+\cdots+9^m$ nodes and the same coarse exponential bound. Counting constraint-checking work separately multiplies this bound by the cost per node. This is a search-size argument for a fixed 9-by-9 board, not an asymptotic hardness result for fixed-size Sudoku [2,4].

Backtracking rejects a partial assignment as soon as it violates a constraint. Later assignments cannot remove an existing duplicate, so every extension of that branch can be skipped. Finding a conflict with k cells unassigned can avoid up to $9^k$ complete assignments. Pruning usually reduces practical work but does not establish a polynomial worst-case running time.

Minimum remaining values (MRV) selects an empty cell with the smallest current domain [2,4]. The implemented solver recomputes candidates from the current board. It does not maintain propagated domains or enforce arc consistency. Separating those techniques matters when explaining where the measured speed differences arise.

\section{Part 1B: Sudoku solver}\subsection{Method and implementation}
The Python solver uses depth-first backtracking with MRV. The board is a list of nine integer lists. solve() validates and copies its input so the caller retains the original puzzle. TXT and CSV readers accept nine rows with nine digits each; zero denotes a blank. Malformed input and conflicting givens are rejected.

For each empty cell, candidates() removes all values already present in its row, column and box from $\{1,\ldots,9\}$. At a search node, MRV scans all empty cells. An empty candidate set immediately rejects the branch; otherwise the smallest candidate set determines the next cell. Ties use top-to-bottom, left-to-right order, and candidate digits are tried in ascending order.

An attempted assignment changes one cell. If recursion fails, that cell is reset to zero before the next digit is tried. No maintained domains need restoring. A complete board is accepted; exhausting all legal branches reports no solution. This finite exhaustive search is complete, although difficult inputs can be slow. A row-major option supplies a controlled variable-ordering comparison.

The CLI returns status 0 for a completion, 1 for no solution and 2 for an input error. A separate completion counter stops after two solutions when testing uniqueness; finding one solution alone does not establish uniqueness.

\subsubsection{Interface additions}
The Tkinter interface provides Load, Solve, Reset and Clear. Load preserves the original puzzle for Reset; Clear removes the board and loaded original. Given digits are black and added digits blue. Duplicate values are highlighted in red, and selecting an empty cell displays its current candidates. Candidate information expresses local legality, not a guarantee of a complete solution. These additions help explain the model without changing the search. Search is synchronous, so expensive inputs can temporarily block the window.

\subsubsection{Correctness checks}
Seventeen solver tests cover parsing, malformed/conflicting input, solved boards, few blanks, several puzzles, no solution, deterministic behaviour, input preservation and CLI return codes. A separate set-based oracle checks rows, columns, boxes and givens. Six interface-state checks cover conflict marking, candidate display, Clear after manual edits and Reset after solving. The interface tests use widget doubles; native window rendering and event bindings still need manual demonstration.

\subsubsection{Theoretical A* formulation}
A state is a consistent partial board. An action assigns one legal digit to one blank cell at unit cost; a goal is a full valid board. Let h be the number of remaining blanks. It is admissible and consistent: any completion requires exactly one action per remaining blank. With m initial blanks, $g+h=m$ at every reachable state. Thus f cannot distinguish branches, and expansion order depends on tie-breaking. FIFO tie-breaking behaves breadth first and retains an unexpanded frontier that can require exponential memory; depth-first backtracking retains a path. No A* implementation or performance measurement is claimed. Forward checking, AC-3 and exact-cover search are possible alternatives [2,4], but their performance was not measured here.

\section{Part 2A/B: Domain and mission design}
The reusable lunar domain uses STRIPS and typing [1,5]. Types are rover, lander and waypoint. belongs-to assigns each rover to one lander; lander-at fixes a landing site; connected represents a directed road. aboard represents an undeployed rover, while rover-at gives a deployed rover position. Actions use parameters, rather than hard-coded rover, lander or waypoint identifiers.

Deployment removes aboard and places the rover at its own lander site. Movement requires an existing directed edge and replaces the old rover position. A lander never moves after landing. Well-formed initial ownership and locations are assumed. Single arrows in the supplied maps are not made bidirectional.

One shared memory-free token prevents carrying two unsent data items: taking either an image or scan consumes it. Sending requires the corresponding held data, rover ownership and current position, restores the token and records image-saved or scan-saved at the receiving lander. Sending is wireless; rover and lander do not need to share a waypoint.

A separate sample-free token permits at most one carried sample, independently of data memory. A sample goal is achieved only by store-sample, requiring the rover at its own lander. Storage consumes the lander storage-free token and restores the rover sample slot. No action restores lander storage, so each lander can store at most one sample.

\subsection{Mission configuration}
Mission 1 fixes Lander 1 at WP1 with Rover 1 aboard and uses the six directed edges of Figure 2. It saves the WP5 image and WP3 scan at Lander 1 and stores the WP1 sample there. Saved base checks compared 2,496 typed action instances in 16 coherent states. A renamed three-rover instance produced a valid 23-action plan. These are targeted tests, not exhaustive proofs or claims of shortest plans.

\section{Part 2C: Astronaut extension}
The extended domain adds astronaut and room types. astronaut-belongs-to assigns an astronaut to a lander; room-of records room ownership. docking-bay and control-room classify rooms, room-connected describes internal links, and astronaut-at records the current room. Every lander has distinct docking and control rooms, connected in both directions.

The move-astronaut action requires the astronaut at the source, a connecting edge and both rooms belonging to that astronaut's lander. It deletes the old location and adds the new one. Even a supplied cross-lander adjacency cannot permit movement into another lander because room ownership is also checked.

Deployment and sample storage require an astronaut in the receiving lander's docking bay. Both data-transmission actions require an astronaut in its control room. The added astronaut and room parameters are checked for ownership, room role and current presence. Existing rover movement, acquisition, memory and sample rules remain unchanged; no astronaut is needed simply to drive or acquire data.

Mission 3 preserves Mission 2's map, rover/lander setup and all six goals. Alice belongs to Lander 1 and starts in its docking bay; Bob belongs to Lander 2 and starts in its control room. The unchanged base setup and required astronaut facts are verified by the validation tool.

\subsection{How the extension changes the plan}
The saved 24-action plan contains four astronaut moves. Bob first moves from control room to docking bay, permitting deployment and later sample storage, then returns to the control room for transmissions. Alice moves from docking bay to control room to permit transmissions, then returns to the docking bay before sample storage. Each dependent action is checked against the corresponding lander and room state; astronaut location therefore changes applicability rather than serving as a decorative fact.

\subsection{Extension validation and limits}
All three missions plan and independently replay successfully. In 23 constructed coherent states, 24,380 typed action instances were checked: 180 allowed instances had the expected effects and 24,200 forbidden instances were rejected. Cases include wrong astronauts, room types, cross-lander movement, co-located landers and inherited capacity rules. Both astronauts move in Mission 3 and every restricted action has a matching astronaut and room. These checks assume valid initial states and do not explore every reachable state.
